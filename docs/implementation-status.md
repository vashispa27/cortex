# Implementation status

## Cortex desktop setup (18 October 2026)

Cortex is now the desktop UI for the `cortex` engine. Its bundled background process runs `cortex desktop`, owns `~/Library/Application Support/Cortex/local-memory/memory.sqlite3` and its Qdrant Edge index, and exposes a private Unix socket adapter for the UI. Both chat surfaces send natural-language questions through the same Model2Vec dense + BM25 sparse retrieval, RRF fusion, version/dedup processing, weak-match decision, and redacted source preparation as the CLI. The Memory page also uses this hybrid retrieval. There is no frontend keyword fan-out, recent-screen fallback, or X/LinkedIn-specific sort. Chat follow-ups are rewritten into self-contained search questions by the selected model, then retrieved locally. The existing OpenRouter model setting and user-only local key file remain in use; no Keychain access is added.

On first start, already-sanitized captures from the former desktop SQLite database are copied into the canonical archive, retaining source URLs and all observation timestamps. A persistent mapping makes the import idempotent; originals remain in the retired database. Imported text is labeled `legacy_sanitized` and does not claim to contain original AX trees. The existing capture opt-in, pause and exclusions are carried over. New capture uses the Cortex cleaner and chunk/index path, excludes Cortex's own windows and credential controls, and retains the desktop's public-browser-only capture behavior. Existing CLI blocklist entries also apply. Capture no longer starts the old `cortex-daemon`. A privacy deletion through the UI clears both archives and rebuilds the disposable Qdrant index; import tombstones prevent old captures from returning.

The adapter identifies itself as `qdrant_edge_hybrid` with the embedding model and indexed chunk count in status. Diagnostics exposes the active retrieval engine. Backend failures surface as errors; they do not trigger a keyword-search fallback. Unit tests cover frontend delegation/follow-ups/errors, migration idempotency and observation timestamps, along with the engine's existing test suite. Native end-to-end verification is recorded below after the updated bundle has been launched.

Native verification (18 October 2026): a stale Cortex build was found running the retired SQLite-only `cortex-daemon`. After quitting it and launching the rebuilt `Cortex.app`, the bundle installed and spawned `cortex-engine desktop` against `local-memory/`, created the `qdrant-edge` index, and imported 320 legacy captures (2,642 indexed chunks). Over the Unix socket, `/v1/status` reported `retrieval_engine: qdrant_edge_hybrid` with the Model2Vec embedding model. `/v1/memory/search` for "what was I working on in Codex" returned Codex sources through dense + BM25 + RRF (40 candidates, 39 collapsed). "olive oil" correctly abstained, returning only weak Amazon matches. Not yet verified: the answer UI through the notch, and live capture, since Accessibility is not granted to the new Cortex capture helper (`permission_state: not_granted`, `capture_enabled: false`).

Follow-up (18 October 2026): the intermittent "memory engine returned invalid data" error came from the engine silently dropping a request when the accepted socket inherited the listener's non-blocking mode; the socket is now blocking and read failures return an error reply. The notch answer panel gained an Expand button, and the dashboard's Ask Cortex page now uses the same persisted sessions as the notch (session list, cross-window sync, selected-session handoff on expand). Answers cannot link to the exact X conversation for the 320 imported captures: the former desktop capture stored only the site origin (`https://x.com`). New captures keep the full address. The rebuilt bundle was launched and six consecutive socket searches succeeded; the new UI was not clicked through.

Accessibility fix (18 October 2026): the engine launches the capture helper from the signed `Cortex Capture.app` bundle and spawns it as its own responsible process (`posix_spawn` with disclaim). Without that, macOS judged the helper under the Cortex app's ad-hoc identity, which changes on every rebuild, so an Accessibility grant never applied. After the change `/v1/status` reported `permission_state: granted` with the existing "Cortex Capture" grant. Live capture of a real window is not yet verified.

Updated 16 October 2026. This document distinguishes implemented behavior from proposed requirements in [the specification](../cortex-end-to-end-spec.md).

## Verified in this workspace

- Snapshot cleaner v3 is implemented in the macOS CLI. The AX helper emits bounded ancestor paths and visible bounds, and SQLite keeps the original `ax_nodes_json` with cleaned `body`, quality, coverage, and per-node removal reasons. A dry run over 61 stored snapshots showed the ChatGPT nutrition recommendation and every cited quantity retained while sidebar, browser controls, prompt box, and feedback controls were removed. The applied migration merged duplicate snapshots, marked navigation-only screens unsearchable, regenerated derived entries, and rebuilt Qdrant with message/paragraph chunks. Eight older captures had no saved AX nodes, so their originals remain in SQLite but are unavailable to the clean index. `ask "olive oil"` retrieved the cleaned ChatGPT source and full URL. This is a local-data verification; a fresh live capture with the new ancestor paths has not yet been inspected.

- The new `cortex` macOS CLI builds and completed a live Accessibility check after the helper was granted permission. Safari exposed a local HTML chat page, its full `file:///private/tmp/cortex-browser-check.html` URL, 20 ordered Accessibility nodes, and a displayed `10:42 AM` message time. `capture --print` stored the screen in SQLite as snapshot #2 and repeated polls updated its sighting count without another snapshot. A later capture of the same page stored all 20 ordered AX nodes in SQLite's `ax_nodes_json` column; 20 observations shared snapshot #3. Local Model2Vec indexed it into Qdrant Edge; `ask` retrieved its original text and URL while capture was running and after capture stopped. A Chrome Incognito window on the same page also exposed the text and full `file:///tmp/cortex-browser-check.html` URL; capture stored it as snapshots #4 and #9 when toolbar metadata changed, with the same message evidence and `some_element_bounds_unavailable:2`. The latter snapshot has `browser_private` source type. The CLI keeps originals in its own SQLite database and offers capture/ask through a private Unix socket while capture runs. The desktop workflow now also reads normal browser windows while skipping private/unknown browser contexts.

- Rust capture policy defaults to no consent, rejects private or unknown browser context, excluded apps/domains/windows, protected UI subtrees, and inactive sessions. It bounds traversal and redacts covered secret formats before hashing and persistence.
- SQLite stores sanitized source versions separately from observations, with transactional FTS triggers. Search uses observation timestamps for date filters. Selective and whole-store deletion advance a memory epoch, remove dependent derived records, pause capture, and return a receipt. Ordinary SQLite deletion does not guarantee SSD or backup erasure.
- The loopback daemon uses a random per-install bearer token in a private state directory, checks Host/Origin, and exposes status, typed settings, search, exact sources, recent and deduplicated working memory, day digests, tracked foreground time, and deletion. Its macOS worker runs only after a persisted capture choice and Accessibility permission. It rechecks pause, exclusions, settings version, and deletion epoch before committing an observation. Synthetic ingestion remains an explicit offline CLI command.
- The MCP stdio bridge uses the official TypeScript SDK and requires the separate `mcp_enabled` setting. It supports shared tasks, expiring claims, handoff packs, immutable transcript imports, follow-ups, attributed permanent memories and the existing capture queries. The desktop socket and older daemon share the workspace implementation. Client registration preserves other strict-JSON entries and removes only an unchanged owned entry. See [shared workspace](shared-workspace.md) for setup and limitations.
- The Tauri shell builds as a macOS app, embeds and starts the daemon, and proxies allowlisted routes without exposing the token to React. Capture settings now offer Start, Pause, Stop, permission request, and applied exclusions. A prior native smoke test connected it to an isolated synthetic daemon, loaded a recent source, and opened its exact stored text; live AX reading remains unverified. The browser sample includes onboarding and evidence browsing. The desktop workspace mounts the real scheduler, intent-routed chat, permanent and recent activity memory, and Agent Space; browser previews show service-unavailable errors for native APIs. The current chat view can send bounded local evidence and recent conversation to the configured OpenRouter model; without a key it returns local search results for inspection instead.
- The shell now includes a native notch Cortex drop with a neon logo, settings and chat controls, a single-entry cortex flow with the cortex animation and answer panel, and a session-history panel with undock. Sessions persist locally. A configurable global modifier double-tap (right/left Option, Globe/Fn, Shift, or Control) opens a fresh cortex and restores the previously frontmost app after submission. The dashboard home groups activity, apps, timeline, reminders, and quick controls; a separate timeline view groups sources by day. A live macOS smoke check confirmed the drop renders above the menu bar, the logo and input are clickable, the input retains keyboard focus, the double-tap opens a fresh cortex, the animation and answer panel render, and the settings and history controls work. Capture remains off by default. Hiding the drop and showing it again from the same-space menu is supported; the cross-space overlay behavior remains an open native polish item.
- The cloud gateway enforces signed OIDC access tokens outside development mode, explicit cloud consent, bounded schemas, idempotency keys, quota, source-ID validation, and format-aware credential rejection. The control service stores metadata rather than an archive. Development mode uses a deterministic mock provider.
- The public website has an original identity, responsive preview pages, and unavailable downloads until artifacts are configured. Release metadata tooling checks an external Ed25519 signature, local artifact hashes, and remote artifact bytes at an allowlisted HTTPS download origin before exporting URLs.

## Native feasibility and release gates

| Gate | Current result |
|---|---|
| macOS AX permission | Granted to the new CLI helper during this check. Safari, Chrome Incognito, and the Codex app were read through Accessibility. Other-app and long-running battery coverage remain unverified. |
| Windows UI Automation | Out of scope for this macOS implementation. An earlier probe remains in the repository. |
| Capture service | The macOS worker polls foreground Accessibility text through a bounded helper only after consent, permission, and exclusions. It reads normal browser windows, skips private/unknown browser contexts and known credential apps, and excludes Cortex itself. Live third-party capture, app compatibility, and resource use still need verification with user-granted permission. |
| Memory quality | Lexical retrieval and deterministic day digests exist. Entity wiki, commitments, style learning, hierarchical summaries, and 200-case evaluation sets are not implemented. |
| Account and cloud | Gateway OIDC verification exists. Desktop PKCE sign-in, credential storage, and production provider configuration remain. |
| Scheduling | Durable service schedules, timezone-aware recurrence, after-wake eligibility and persisted run history are implemented. Generated tasks require a provider; live sources require hosted search access. See [scheduler](scheduled-tasks.md). |
| Distribution | Manifest verification and CI definitions exist. Signed/notarized installers, updater, rollout, performance/battery results, and production deployment remain. |

Do not enable personal capture, external AI client access, or cloud processing as a side effect of building or verifying the app. Each needs its own explicit user choice and OS permission where applicable. A macOS release requires native app validation and the quality/security gates in spec section 16.
